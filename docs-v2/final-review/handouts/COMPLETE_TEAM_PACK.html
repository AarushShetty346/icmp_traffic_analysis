Cadence — 15-minute, three-person review

Order: You → Harsh → Aarush. One laptop, one browser session. Each person speaks for roughly five minutes and leaves the next person's chapter open.

The single story

A sender hides 0s and 1s in the pauses between ordinary ping requests. We first inspect those pauses, then test whether a defender can spot or disrupt the message without harming normal traffic. Finally, we encrypt the note and ask what the defender can still learn. The site makes those ideas visible and gives us a workbench to test them; the included network runs are simulated.

Keep coming back to three questions: Can the receiver read the bits? Can the guardian notice the timing? What does the defence cost ordinary traffic?

Exact handoffs

  2. Harsh → Aarush: Return to Guided case, open Locked note in the chapter bar. Say: “A guardian can see timing and can even disrupt it. Aarush will show what changes when the note itself is encrypted.” Hand him the laptop.
  3. Aarush → panel: Finish on Evidence. Say: “Our software and browser encryption work, and the simulations show the trade-offs. The next claim needs real receiver-side captures; the page states that limit openly.”

Keep these claims precise

  • 610 included runs are simulated; zero included receiver captures are real. The CSV importer accepts a user's capture, but importing a file does not prove how it was collected.
  • The guided case computes from the included dataset. A high detection percentage is a result for a small controlled set of windows, not a universal accuracy guarantee.
  • The paced relay is a causal browser model that holds packets; it has not been deployed on a router.
  • AES-256-GCM encryption is performed by the browser's Web Crypto API. The encrypted bytes' timing delivery is simulated, with no ICMP packets sent by that scene.
  • Our contribution is the integrated investigation and evaluation workflow: sender idea → receiver evidence → detector errors → defence cost → encrypted content → evidence limits. We are not claiming to have invented AES or covert timing channels.

Presenter 2 — Harsh: guardian and defence (5:00–10:00)

Your question: Can we detect or disrupt the hidden timing without accusing ordinary traffic or delaying it too much? You own Guardian, Detectors, and Stress matrix. You do not need to re-teach the sender's 0/1 encoding; the first speaker has done that.

Start screen: Guided case — Guardian. End screen: Guided case — Locked note. Leave the mouse with Aarush.

Your five-minute route

5:00–5:45 — Explain what a guardian actually judges

Point to the three rule choices. Say:

“We should not declare an attack from one unusual pause. This guardian judges a small group of 32 requests. It measures how much their gaps vary, then compares that with a limit. We test three ways to choose the limit: one fixed number, a limit learned from ordinary traffic under the same conditions, and a limit learned only on a clean network.”

Plain terms: a window is one group of requests; a baseline is a normal reference used to choose a limit; standard deviation means how much the pauses wobble around their average.

5:45–6:45 — Compare the rules, including mistakes

Begin on Same conditions. Point to Messages caught and False alarms together. On the default example they show 10/10 caught and 3/10 ordinary windows falsely flagged. Click Fixed limit: it usually shows 0/10 caught, 0/10 false alarms on this default example. Click Clean-only baseline: it shows 10/10 caught but 10/10 false alarms. Return to Same conditions.

“If a rule never sounds the alarm, its false-alarm rate looks perfect but it misses the message. If it alarms on everything, it catches the message but becomes useless for ordinary users. The same-conditions baseline is more sensible here, yet even it still wrongly flags some normal traffic. These figures describe this small simulated set, not an accuracy guarantee for the Internet.”

Read the live figures if the condition or dataset was changed. Do not memorize a percentage without its numerator and denominator.

“These squares are the actual decisions behind those percentages. The ordinary row shows the cost of mistakes; the message row shows what was caught. That is why we report both numbers together.”

If you get a question

  • “What exactly is the learned limit?” The guided baseline uses the 95th-percentile standard deviation from separate ordinary 32-request windows; it alarms when a test window exceeds it.

The local V2 passed 72 UI unit tests, 62 Python tests (2 skipped), a production build and size check, and 32 desktop/mobile browser checks (4 intentionally skipped). Browser checks include navigation, encryption success/failure, accessible controls, and layout widths. These checks support software correctness, not real-network accuracy. Terms to avoid mixing up

  • Detection rate = message windows flagged / all message windows.
  • False-positive rate = ordinary windows wrongly flagged / all ordinary windows.
  • Bit recovery = correct bits / expected bits; a high percentage can still leave the whole encrypted note unreadable.
  • Encryption protects content; encoding maps bits into timing; detection judges observed timing; pacing delays release to reduce that timing pattern.
  • Simulated run is generated data. Real capture requires actual receiver-side packet timestamps and a trustworthy record of how they were collected.
